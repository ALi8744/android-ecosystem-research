# Security Policy

Thank you for helping keep this project secure. This document explains how to report security vulnerabilities and how we handle reports for the Unified Update Experience Framework for the Android Ecosystem.

Security contact

- Preferred: Open a private security issue on GitHub if private issues are enabled, or use GitHub's security advisories to report a vulnerability: https://github.com/ALi8744/android-ecosystem-research/security/advisories
- If you cannot use the repository's security reporting mechanisms, contact the maintainer directly via their GitHub profile: https://github.com/ALi8744

Please do NOT disclose vulnerability details publicly until the issue is resolved and coordinated disclosure has occurred.

Reporting a vulnerability

When reporting a potential vulnerability, please include the following where available:

- A clear, concise summary of the issue.
- Steps to reproduce (including minimal reproduction code, test cases, or sample inputs where appropriate).
- The impact of the issue (confidentiality, integrity, availability, privacy, or other user harm).
- Affected versions or files, and whether the issue applies to documentation, scripts, or deployed systems.
- Any suggested mitigations or patches you believe are relevant.

Preferred format

- If possible, provide a short numbered list of reproduction steps and a minimal example that demonstrates the problem.
- Attach patches as diffs or PRs against the main branch in a draft PR or in a separate private communication channel.

Our process

1. Acknowledgment: We will acknowledge receipt of your report within 5 business days.
2. Triage: We will assess the report and classify severity and impact. We may ask follow-up questions or request additional information to reproduce the issue.
3. Remediation: For confirmed issues, we will prioritize remediation and preparing an appropriate fix or mitigation strategy.
4. Disclosure: We will coordinate disclosure with the reporter. We aim for responsible disclosure that gives maintainers and downstream users time to apply fixes before public release.

Timeline and expectations

- Initial acknowledgment: within 5 business days.
- Triage and initial assessment: typically within 10 business days, depending on complexity and available information.
- Fix and release timeline: depends on severity and required changes. Critical issues will be prioritized, but timelines vary.

Public disclosure and CVEs

- For vulnerabilities affecting code that could merit a CVE, we will coordinate with the reporter about whether to request a CVE and how to handle public disclosure.

What we expect from reporters

- Please avoid public disclosure of vulnerabilities before we have remedied the issue and coordinated disclosure.
- Provide enough information to reproduce the issue — vague reports slow the response process.
- Be available for follow-up questions during triage and remediation.

Sensitive data and merge requests

- Do not attach live secrets, credentials, or private data in public issues or PRs. If you must share sensitive materials to reproduce an issue, request a secure channel from the maintainer.

Limitations

- This repository is research- and documentation-focused and does not run user-facing infrastructure under the project name. Security reports about third-party services, vendor platforms, or external ecosystems should be reported to the responsible party for that software or platform.

Acknowledgements

We appreciate security researchers and contributors who help improve the safety of this project. If you request attribution, we will credit you in the security advisory or changelog unless you explicitly request anonymity.
